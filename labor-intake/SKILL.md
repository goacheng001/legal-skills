# labor-intake — 劳动争议接案审查

## 工作定位

**职责**:对新接的劳动争议案件做"准入体检",输出**接案审查报告**,写入 `intermediate/劳动覆盖层/L1-接案审查/接案审查报告.md`,并把立场(claimant/respondent/adjudicator)、时效状态、conflict_check 等写入 `labor-os-state.json`。

**前置条件**:
- 案件目录已由 case-os 创建(含 `CLAUDE.md`、`LOG.md`、`_archive/`);若用户首次接入且 case-os 尚未创建,先调用 `case-os` 或 `case-git-init` 创建案件骨架。
- 已有 `劳动争议案件事实摘要`(用户提供或劳动OS前置问答生成)。

**独立触发保障**(被直接调用时):
1. 加载 `labor-os/references/redlines-labor.md`;
2. 加载 `labor-os/references/ldzy-entity-routing.md`;
3. 尝试读取 `案件目录/_archive/labor-os-state.json`,若存在 → 继承 track/stance 不再问;
4. 若不存在 → **必须先询问一次立场**;
5. 加载 `labor-os/references/knowledge/主体资格坑点清单.md`、`举证责任分配表.md`、`仲裁流程时限表.md`、本主题库;
6. 确认可加载 `ldzy-labor-relation-id`（及按需 `ldzy-case-acceptance-filter` / `ldzy-special-forms-subjects`）。

**必须确认**:是(立场三选一与时效红线均需用户书面确认)。

**执行后 Hook**:否(本skill产出物供下游 skill 消费;hook 由劳动OS总控在适当时机触发)。

**位置层**:L1(劳动覆盖层第一步)。

---

## 执行流程

### 步骤1 收集基本信息【完成判据:当事人工种日期齐全】

向用户依次询问并记录:
1. **当事人**:
   - 劳动者(姓名/年龄/入职日/岗位/合同类型与期限);
   - 用人单位(全称/统一社会信用代码/注册地与实际经营地);
   - 是否涉及分支机构、劳务派遣、关联公司(混同用工);
2. **用工事实**:岗位职责、工作地点、工时制、薪酬结构;
3. **争议事项**:欠薪/加班费/解除补偿/工伤待遇/竞业限制/股权激励等;
4. **关键日期**:
   - 入职日 / 离职日 / 解除通知日;
   - 欠薪起止日 / 加班终止日;
   - 已知权利被侵害日(如工伤事故日、解除通知送达日)。

### 步骤2 立场三选一【完成判据:写入labor-os-state.json.stance】

向用户出示:

```
【立场三选一】
1. claimant — 代理劳动者(申请人侧)
2. respondent — 代理用人单位(被申请人侧)
3. adjudicator — 裁判者(高澄以仲裁员/法官身份办案)
```

**裁判者分支(选3时立刻执行)**:
- 询问:本案当事人是否与你代理过的客户/顾问单位存在**利益冲突**?
- 若回答"有"或"待查" → 在 labor-os-state.json.conflict_check.result 记"need_recusal",**提示用户回避**;
- 若回答"无" → 记"clear",继续。
- **保密隔离生效**:不再向顾问轨知识沉淀推送本案材料。

立场选定后写入 `labor-os-state.json.stance`,后续 skill 继承,**不再重复询问**(立场继承铁律)。

### 步骤3 劳动关系审查【完成判据:ldzy 四规则痕迹+特殊主体排查】

**强制**:加载并执行 `ldzy-labor-relation-id` 的 **E 步骤**(推定提供劳动 → 事实优先名实审查 → 形式标志/实质辩证 → 平台三类若适用)。  
禁止仅复述「主体+管理报酬+业务组成」口号而不给出举证顺序与名实结论。

可并行:
- 请求能否进仲裁 → `ldzy-case-acceptance-filter`(简表即可);
- 派遣/外包/混同/学生/超龄/董监高等 → `ldzy-special-forms-subjects`;
- 弱从属中间带 → `ldzy-complete-incomplete-triage`(须标 B 边界,禁止当全国强制法)。

对照 `主体资格坑点清单` 与 ldzy 特殊主体速查交叉校验。

**输出**:
1. 四规则推进记录(每步完成标准勾选);
2. 关系定性结论(完全劳动 / 需不完全分诊 / 民事 / 待证);
3. 特殊主体/形态风险清单;
4. 可选写入 `labor-os-state.json.ldzy.invoked`。

### 步骤4 仲裁时效审查【完成判据:逐项请求独立计算+首屏预警】

这是**首屏必做**的强提示。

1. 列出每项请求对应的**主张日(知道或应当知道权利被侵害日)**;
2. 逐项计算**1年时效的届满日**;
3. 区分:
   - **一般请求**:立案/解除通知/欠薪等 → 1年;
   - **劳动报酬存续期间不受限**,但**劳动关系终止后1年内**;
   - 工伤:以《工伤保险条例》时效口径,依事故日/认定日/伤残鉴定日分别计时;
4. **如有 ≥1 个请求已过或 30 日内届满** → 输出**首屏红字预警**(时效红线),不得埋在正文;
5. 中断/中止法定事由的初步核查(如已催告、已申请监察、已向企业主张)。

**输出**:`limitation.deadline` 列表 + `limitation.status`(ok/warning/expired)。

### 步骤5 管辖判断【完成判据:1个首选+1个备选+抢管辖提示】

- 劳动合同**履行地**与用人单位**所在地**分列;
- 谁更有利(从证据、证人、判例倾向等角度);
- **抢管辖提示**:建议方向(仲裁阶段与诉讼阶段可不同);

### 步骤6 证据缺口初判【完成判据:三栏对照表】

按立场生成"我需举证项 - 已有 - 缺口"三栏对照表:
- 申请方:主张 = 解除违法/欠薪/加班 → 已有证据 → 缺口清单;
- 被申请方:抗辩思路 → 已有证据 → 缺口清单;
- 裁判者:双方均需呈现。

参照 `举证责任分配表` 的 8 条倒置规则,逐项标记倒置项。

### 步骤7 双轨联动(裁判者立场跳过)【完成判据:扫描完成或用户确认跳过】

询问用户:**该当事人(尤其用人单位)名是否在你们顾问项目目录中存在旧档?**

- 是 → 列出旧档清单(项目目录、关联服务、关联主体)→ **提示"有历史关联,审慎处理"**;
- 否 → 记录"无旧档关联";
- 用户跳过 → 记录"用户选择跳过"。

⚠️ 裁判者立场时**跳过本步**(避免双向利益输送)。

### 步骤8 报告生成 + labor-os-state.json 写回【完成判据:文件存在+JSON结构合法】

写出 `intermediate/劳动覆盖层/L1-接案审查/接案审查报告.md`,frontmatter 含:
```yaml
---
step_id: L1
track: dispute
stance: <claimant|respondent|adjudicator>
limitation_status: ok|warning|expired
status: pending_review
created_at: 2026-MM-DD
---
```

**正文必须包含**:
- 1. 基本信息复核;
- 2. 立场确定(及裁判者分支时的利益冲突自检结论);
- 3. 劳动关系三要素判断 + 特殊主体风险;
- 4. **时效审查逐项列表(独立计算)** + 首屏预警(如有);
- 5. 管辖建议 + 抢管辖提示;
- 6. 证据三栏对照表;
- 7. 双轨联动核查结果(裁判者时 N/A);
- 8. 待用户确认事项 list。

报告生成后:
- 询问用户"是否确认" → 用户确认后写入 `labor-os-state.json`(stance/conflict_check/limitation/arbitration.deadlines[]);
- 把 `labor-os-state.json.workflow.l1_intake` 标记 completed;
- 返回劳动OS总控或下游仲裁 skill。

## 红线

引用 `labor-os/references/redlines-labor.md`,本skill特有补充:
1. **时效红线**:已过或30日内届满 → 首屏红字预警,不得埋在正文;
2. **属地红线**:引用浙江口径必须显式标"依浙江口径",**未标不得交接**给下游仲裁 skill;
3. **裁判者红线**:立场为 adjudicator → 立即执行利益冲突自检 + 启用保密隔离。
